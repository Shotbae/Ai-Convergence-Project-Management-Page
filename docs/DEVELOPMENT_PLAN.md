## 2. 개발 항목 A: 이수자 명단의 기수 선택

### 2.1 상단 메뉴와 생성 화면

상단 `⚙️ 출석부 관리` 메뉴의 `최종 이수자 명단 생성`을 누르면 설정 팝업을 연다. 팝업에는 생성 방식 드롭다운, 기수 드롭다운, 생성 버튼을 둔다.

| 생성 방식 드롭다운 | 기수 선택 | 결과 |
| --- | --- | --- |
| 선택 기수 명단 생성 | 필수 | 선택한 기수의 `{기수}_최종이수자명단`만 생성 |
| 전체 기수별 명단 생성 | 사용하지 않음 | 기존처럼 기수마다 별도 명단 생성 |
| 전체 통합 명단 생성 | 사용하지 않음 | 모든 기수를 `최종이수자명단` 한 시트에 취합 |

`전체 통합 명단`은 기존 코드에 있는 기능으로, 1기·2기·3기 등 모든 기수의 이수 내역을 한 시트에 모은다는 뜻이다. 같은 학생이 여러 강좌를 이수하면 강좌별로 여러 행에 표시된다. 학생 한 명의 여러 이수 내역이나 세특 내용을 한 행으로 합치는 기능은 아니다.

- 기수 목록은 실제 출석부 시트명에서 추출하고 숫자순으로 정렬한다. 예: 1기, 2기, 10기.
- `선택 기수 명단 생성`일 때만 기수 드롭다운을 활성화한다.
- 기존 출석부 생성용 `출석부생성!B3:B4`에 작업 설정을 덮어쓰지 않고 생성 함수에 선택값을 전달한다.
- 생성 중 중복 클릭을 막고, 완료 후 생성·기존 시트 유지·이수자 없음 등의 결과를 안내한다.
- 기수를 선택하지 않거나 창을 취소하면 명단을 변경하지 않는다.

### 2.2 이수 판정과 명단 보호

- 출석부의 B3 강좌명, B5 담당교사, E7/F7의 수업 일수, 8행 이후 B~F를 필요한 일수만큼 읽는다.
- 1일 강좌는 D, 2일 강좌는 D/E, 3일 강좌는 D/E/F가 모두 `true`인 학생을 수집한다.
- 기수 판정은 이름의 정확한 기수 부분으로 수행해 1기와 11기를 혼동하지 않는다.
- 기존 대기자 표기 정리와 출석을 충족한 대기자의 이수 처리 등 현행 판정은 그대로 대조한다.
- 기존 명단의 G열 수기 내용을 보호한다. 기본 생성 동작은 이미 있는 명단을 유지하는 방식으로 설계하며, 기존 통합 함수의 무조건 `clear()` 경로를 제거하는 안을 적용한다.
- 기존 명단을 갱신·병합하는 기능이 필요하면 학생·기수·강좌의 유일한 식별 기준을 먼저 확정한다. 강좌 이름만 보고 서로 다른 기록의 세특을 합치지 않는다.
- 이수자가 0명인 기수는 생성하지 않고 해당 사실을 안내한다.

### 2.3 사용자 승인 1~3일 공통 출결 판정 (2026-11-05 구현)

- 기존 E7의 2일차 유무 기준을 유지하고, F7이 날짜 또는 `3일차`·`3차시` 표기일 때 3일 강좌로 읽는다. 기존 `비고`·`서명`은 3일차로 오인하지 않는다.

- 3일 강좌는 셋 중 어느 하루라도 미체크·빈칸이면 이수자에 포함하지 않고 결석 이력으로 집계한다. `(대기)` 학생의 전일 미참여 제외 기준도 세 날 전체로 확장한다.

- 수동 합산 후 남는 추가 수업 출석부는 사용자가 보관용 이름으로 변경해 별도 집계에서 제외한다. 기존 이수자 명단은 보호를 위해 계속 건너뛰므로 새 판정의 반영은 세특 백업 후 재생성 절차를 따른다.

## 3. 개발 항목 B: 생기부 검증기의 로컬 규칙 이식

### 3.1 가져올 코드와 범위

생기부 검증기 프로젝트의 다음 Python 코드를 JavaScript로 옮긴다. Java가 아니라 Google Apps Script에서 실행할 JavaScript다. 외부 AI 호출 없이 규칙과 예외 조건으로 검사한다.

| 원본 | 가져올 내용 | 계획 작성 시점 SHA-256 |
| --- | --- | --- |
| `setc_checker/engine/local_rules.py` | `check_local_rules(text)`와 관련 검사·문맥·문자 처리 함수 | `C2AB5A8D29FC6C40ECDAE0EBD324CDE200D15F7F06633890C8AECB526A1C1594` |
| `setc_checker/engine/rule_exceptions.py` | 명칭·민감표현 예외, 외국어 예외, 기호 정책 | `17F558229C92073F037433A269A7DAF6B3E779B83ECCA959280EF0AD3FCE1005` |

원본 규칙 버전은 `LOCAL-RULES-v2.2.6-cjk-foreign-text`다. 실제 개발 시작 시 버전과 해시를 다시 확인하고, 변경됐다면 어느 버전을 이식하는지 기록한다. 생기부 검증기 원본 프로젝트는 수정하지 않는다.

이식 대상은 단일 세특 본문에서 수행하는 다음 검사다.

1. 사기업·서비스·국제기구·기관·심리검사·기술 약어 등 명칭 검사와 좁은 예외 처리.
2. 공인어학시험, 모의고사·전국연합, 대회, 도서 출간, 지식재산권, 장학금, 자격증 관련 표현 검사.
3. 영어·한자·중국어·일본어 등의 문자 검사와 현행 `AI` 독립 토큰 예외.
4. 연속 공백, 숨은 문자, 비표준 공백 검사.
5. 허용·확인 대상·금지 기호와 숫자 범위 하이픈 처리.
6. 종결어미 검사와 현행 중간 인용문 예외.

위 단일 본문 검사의 검출 기준·허용 예외·오류 사유는 원본과 동일하게 이식한다. 실행 언어를 JavaScript로 옮기되 판정 기준은 변경하지 않는다. 동일 입력에 대한 원본 Python 검사 결과를 대조 기준으로 삼으며, 규정 해석을 새로 추가하거나 키워드를 임의로 삭제하는 작업은 별도로 다룬다. 원문 내 표시 위치 수집과 G/I열 연결은 시트에 맞게 구현한다.

### 3.2 결과 문구와 판단 의미

- I열 제목은 `오류 사유`로 한다.
- I열에는 `검출 표현: 원본 오류사유` 형식으로 실제 검출된 결과만 출력한다. 여러 항목은 셀 안에서 줄바꿈한다.
- `사기업 명칭 (영상/스트리밍)`, `지식재산권 관련 표현 확인 필요`, `대회 참여/수상 기재 의심`, `금지기호 사용(수정필요)` 등 원본 문구를 유지한다.
- 모든 검출을 일괄적으로 `수정필요` 또는 `확인필요`라는 새 분류로 바꾸지 않는다.
- 원본의 `REVIEW`와 `LIKELY_VIOLATION` 의미를 보존한다. `LIKELY_VIOLATION`을 확정 오류로 바꿔 표현하지 않는다.
- 빨간 글씨는 교사가 살펴볼 자동 검출 대상을 뜻한다. 수정·확인 필요 여부는 출력 사유와 실제 문맥을 함께 보고 교사가 판단한다.
- 검출이 없으면 I열을 비운다. 이는 규칙에서 검출된 항목이 없다는 뜻이며 문장 전체의 정확성을 보증하는 의미는 아니다.

예시에서 `【 】`는 빨간 표시 구간을 설명하기 위한 기호다. 실제 G열 원문에 이 기호를 삽입하지 않는다.

| G열 표시 예시 | I열 출력 예시 |
| --- | --- |
| `【유튜브】 영상을 분석함.` | `유튜브: 사기업 명칭 (영상/스트리밍)` |
| `【특허】의 원리를 조사함.` | `특허: 지식재산권 관련 표현 확인 필요` |
| `【대회에 참가함】.` | `대회에 참가함: 대회 참여/수상 기재 의심` |
| `실험 결과를 발표함【~】` | `~: 금지기호 사용(수정필요)` |

### 3.3 정확한 빨간 표시를 위한 처리

- 검사 함수는 오류 사유와 함께 원문에서의 검출 시작·끝 위치를 반환하는 순수 함수로 구성한다.
- Python의 문맥 문자열 `【…】`을 다시 검색하는 방식에만 의존하지 않는다. 같은 단어가 반복되거나 허용 문맥과 문제 문맥이 공존할 때 다른 위치를 칠하지 않도록 원래 매치 위치를 사용한다.
- 같은 표현이 여러 번 나올 때 유효한 검출 위치를 모두 수집하고, I열의 같은 사유는 필요에 따라 묶는다. 원본 보고서가 일부 규칙에서 첫 문맥만 출력한다는 점과 구분해 검증한다.
- 겹치는 검출 구간은 표시할 범위를 합치되 각 오류 사유는 보존한다.
- JavaScript 문자열의 UTF-16 위치와 Python 문자 위치의 차이를 처리한다. 이모지·확장 한자 뒤에 나오는 표현도 정확한 위치를 칠해야 한다.
- 공백·숨은 문자는 해당 위치를 처리하고, I열에 공백 개수나 문자 종류를 보여 교사가 위치와 원인을 알아볼 수 있게 한다. 검사를 위해 G열에 눈에 보이는 대체 문자를 넣지는 않는다.
- `RichTextValue`로 G열의 검출 구간만 빨간색을 적용한다. 재검사에서 사라진 오류의 이전 빨간 표시는 해제하고 실제 원문과 필요한 기존 서식은 보존한다.

### 3.4 사용자 승인 추가 규칙 (2026-11-05 구현)

원본 검증기에서 가져온 검사 기준은 유지하고, 다음 두 앱 전용 검토 규칙을 함께 실행한다.

| 조건 | 오류 사유 | 검토수준 |
| --- | --- | --- |
| 독립 자모(`ㄱ~ㅎ`, `ㅏ~ㅣ`) 2개 이상 연속 | `자모 연속 표기 오타 가능성(확인필요)` | `REVIEW` |
| 한 글자짜리 완성형 한글 어절 3개 이상 연속 | `한 글자 어절 연속 사용(확인필요)` | `REVIEW` |

- 정상 예시인 `한 번 더`, `두 달 전`, 의도적으로 쓴 `ㄱㄴ`도 확인 후보로 표시한다.
- G열의 해당 구간을 빨간 글씨로, I열에 `표현: 사유` 형식으로 출력한다. 교사가 확인하고 수정하며 자동 교정하지 않는다.
- 한 글자 어절은 공백으로 나뉜 단위를 세며 부분 단어는 세지 않는다. 구절 앞뒤의 일반 괄호·따옴표·문장부호는 표시에서 제외하고 문장부호·줄바꿈에서는 연속 구간을 끊는다.
- 원본 부분은 Python 기준 사례 1,238건으로 계속 대조하고, 추가 규칙은 별도의 경계·표시 시험으로 검증한다.

### 3.5 사용자 승인 연속 스페이스 자동 정리 (2026-11-05 구현)

앞선 본문 보존 계획에서 사용자 승인 범위인 일반 스페이스 정리만 변경했다.

- G열에서 일반 스페이스(`U+0020`) 두 칸 이상 연속 구간마다 첫 한 칸만 남긴다. 문장 앞뒤도 한 칸을 남기며 별도로 잘라내지 않는다.
- LF·CRLF·CR 줄바꿈, 탭·NBSP·전각 공백 등 다른 문자는 그대로 둔다.
- 정리한 문자열로 원본 규칙과 추가 규칙을 실행하고 G열을 실제로 갱신한다. 빨간 표시 위치와 I열 사유도 이 문자열에서 계산한다.
- H열의 기존 G열 참조 바이트 계산 수식을 유지해 정리된 본문 길이로 재계산한다.
- 남는 글자의 원래 위치를 추적해 굵기·글꼴·링크 등 기존 부분 서식을 새 위치로 옮긴다. 글자 색은 기존 검증 기능이 관리한다.
- 입력 확정과 전체 재검증이 같은 처리 함수를 사용한다. G열 수식·I열 사용자 자료 보호와 최신 입력 재확인도 유지한다.
- 순수 원본 규칙 함수에는 공백 정리를 넣지 않아 Python 기준 대조를 유지한다. 시트 흐름에서는 정리 후 검사하므로 제거된 연속 공백의 사유는 출력하지 않는다.

### 3.6 사용자 승인 어미·문장부호 검토 (2026-11-05 구현)

- 원본의 `LOCAL-ENDING` 받침 검사와 Python 대조 결과를 유지한다. 새 검사에는 별도의 종결 후보 목록·일반 명사 예외·연결 표현 예외를 사용한다.
- 종결 후보 어절 뒤 공백/줄바꿈만 있고 다른 한글 어절이 이어지면 `문장부호 누락 의심(확인필요)`을 출력한다. `됨을`처럼 조사가 붙은 형태, 따로 쓴 조사, `함 자체가…` 등의 연결 표현과 닫힌 일반 인용문은 제외한다.
- 본문 끝의 공백·닫는 괄호·따옴표를 제외한 마지막 한글 어절에 문장부호가 없으면 `문장 끝 온점 누락(확인필요)`을 출력한다. 원본 어미 오류와 겹치면 두 사유를 함께 유지한다.
- 두 유형 모두 `REVIEW`로 처리하며 해당 어절만 빨간색으로 표시한다. 문장부호 자동 삽입은 하지 않는다.
- 중간 문장의 종결 여부는 형태로 추정하므로 오탐·누락이 가능하다. 모든 어미·오탈자를 포괄하는 문맥 분석 기능으로 안내하지 않는다.
- 따옴표와 어절을 순회하며 UTF-16 위치를 수집한다. 닫히지 않은 따옴표 반복·긴 무공백 한글에서도 반복적인 전체 본문 재검색을 피한다.

## 4. 시트 편집과 기존 명단에 연결하는 방식

### 4.1 적용 대상과 편집 흐름

대상은 `최종이수자명단` 및 정확히 `{숫자}기_최종이수자명단` 형태인 시트의 2행 이후 G열이다.

1. 사용자가 G열 입력·수정을 확정한다.
2. 편집 이벤트 범위와 G열이 겹치는지 확인하고 실제 셀의 최신 문자열을 읽는다.
3. 연속 일반 스페이스를 한 칸으로 정리하고 로컬 규칙 검사를 실행한다.
4. G열에 정리된 본문과 검출 구간의 빨간 글씨를 적용하고 I열에 사유를 출력한다. H열 바이트 수식도 이 본문을 참조한다.
5. G열을 지우면 검출 표시와 I열 사유도 지운다.

- 입력 중 매 글자마다 검사하는 방식이 아니라 셀 편집 확정 후 검사하는 방식이다.
- H열의 기존 `GET_NEIS_BYTE` 수식은 보존하며 정리된 G열 기준으로 계산한다.
- 여러 행 붙여넣기도 처리한다. 단일 셀 편집에서만 제공되는 이벤트 값에 의존하지 않는다.
- 빠른 연속 수정·동시 편집으로 예전 내용의 결과가 새 입력을 덮지 않도록 최신값 재확인과 필요한 잠금 처리를 설계한다.
- 검사 실패를 검출 없음으로 표시하지 않는다. 처리 실패와 규칙 검출 사유를 구분해 재검증할 수 있게 안내한다.

### 4.2 일괄 재검증과 기존 시트 지원

- 이미 작성된 G열과 이벤트 누락·대량 붙여넣기를 위해 상단 메뉴에 `세특 전체 재검증`을 제공하는 안으로 설계한다.
- 일괄 검사 범위는 이수자 명단 시트로 한정한다. 실행 한도를 넘을 수 있는 대량 작업은 범위를 나눠 처리하고 완료 여부를 알린다.
- 기존 명단에 I열 제목·너비·줄바꿈 서식을 추가할 때 승인된 연속 스페이스 정리 외의 G열 본문과 H열 수식, I열 밖의 사용자 자료를 보존한다.
- 기존 I열에 다른 사용자 자료가 있다면 덮어쓰지 않고 충돌을 안내한다.
- 새 명단의 헤더·테두리·서식은 A:I까지 작성하도록 생성 함수를 연결한다.
- 최종 전달물은 기존 운영 코드에 기능을 통합한 전체 Apps Script 코드다. 중복된 전역 함수가 있는 `.gs` 파일 두 개를 동시에 넣는 구성이 되지 않게 한다.

### 4.3 사용자 승인 헤더 자동 필터 (2026-11-05 구현)

- 새 명단은 세 생성 방식 공통 작성 함수에서 A1:I의 마지막 학생 행까지 필터를 만든다.
- 기존 명단은 전체 재검증에서 필터를 준비한다. 기존 값·세특·수식·행 순서는 유지한다.
- A1에서 시작하는 기존 필터의 범위가 부족하면 I열과 마지막 기록까지 확장하며 열별 조건을 복사한다. 이미 충분하거나 더 넓은 필터는 유지한다.
- 다른 위치의 사용자 필터는 덮어쓰지 않고 범위 확인 안내를 남긴다. 문장 검증은 계속한다.
- 범위 확장이 실패하면 이전 범위·조건을 복원하고 실패를 알린다.

## 5. 학생·강좌 간 중복·유사도 검사: 보류 유지 확정

앞서 나열한 메시지 중 `교과 기록 간 내용 완전 동일`, `영역 간 높은 유사도`, `타 학생과 높은 유사도` 등은 `local_rules.py`가 아니라 별도 `duplicates.py`에서 나온다. 단일 G열 본문만 검사해서 얻는 결과는 아니다.

**2026-11-04 사용자 결정에 따라 학생·강좌 간 중복·유사도 검사는 보류 상태를 유지한다.** 이번에 합의한 G열 입력 후 규칙 검사의 구현 범위는 3절의 단일 본문 검사다. 따라서 원본과 동일하게 가져오는 범위는 해당 문장 검사 기능이며, 별도 중복 엔진까지 전부 이식하는 계획은 아니다.

단일 본문 검사는 이 범위로 구현했다. 중복·유사도 검사는 사용자의 별도 개발 지시가 있을 때 다음 기준으로 후속 계획을 구체화한다.

- 같은 학생의 서로 다른 강좌·기수와 다른 학생의 기록을 어떤 범위로 비교할지 정한다.
- 통합 명단과 기수별 명단에 복사된 같은 이수 기록을 자기 자신과 비교하지 않도록 식별한다.
- 교과·학기/창체·영역으로 설계된 원본 자료 구조를 강좌·기수에 어떻게 대응할지 정한다.
- 원본 95% 유사도 기준과 문자열 정규화·유사도 계산을 대조한다. 임의의 다른 계산기로 같은 결과라고 간주하지 않는다.
- 비용이 큰 전체 기록 비교는 별도 일괄 실행으로 설계하고, 결과에 비교 상대를 표시한다.

검증은 합성 문장과 테스트용 시트로 시작한다. 원본 검증기 결과와의 대조는 자동 규칙의 동작 일치 확인이며, 교사가 판정한 정확도 100%를 뜻하지 않는다. 실제 Google 시트에서 확인하지 않은 단계는 미검증으로 기록한다.
