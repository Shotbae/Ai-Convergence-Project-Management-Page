# 구현 및 검증 기록

작성일: 2026-11-04 (한국 시간)
최종 수정: 2026-11-05 (한국 시간)

## 구현 범위

- 생성 방식 3개와 기수 선택 팝업, 정확한 기수 필터, 숫자순 기수 목록.
- 기존 전체 통합·전체 기수별 생성 함수명과 메뉴 유지.
- 기존 명단을 유지해 G열 수기 세특 보호. 새 명단은 A:I 헤더와 H열 바이트 수식 작성.
- 원본 로컬 문장 규칙과 예외 조건을 JavaScript로 이식.
- 사용자 승인 추가 규칙: 독립 자모 2개 이상 연속, 한 글자 한글 어절 3개 이상 연속을 모두 REVIEW로 검출.
- G열 검출 구간의 빨간 글씨, I열 원본 사유, 수정·삭제·여러 행 붙여넣기 처리.
- G열 일반 스페이스 두 칸 이상을 한 칸으로 자동 정리하고 정리된 본문으로 G열 표시·I열 사유·H열 바이트 수식 결과 갱신. 줄바꿈·나머지 본문·부분 서식·링크 보존.
- I열 기존 자료·수식 충돌 방지, G열 수식 보존, 오래된 입력 결과 쓰기 전 재확인.
- 일괄 재검증 200행 처리와 다음 위치 저장·이어가기.
- 학생·강좌 간 세특 중복·유사도 검사는 보류 유지.

## 원본 규칙 고정과 재현

`tests/reference/local_rules.py`, `tests/reference/rule_exceptions.py`는 이식한 Python 원본 사본이다. 원본 파일 해시를 테스트에서 검사하며 두 파일을 수정하지 않고 비교 기준으로 사용한다. 생기부 검증기 원래 프로젝트는 변경하지 않았다.

- 규칙: `LOCAL-RULES-v2.2.6-cjk-foreign-text`
- `checkSetcReferenceRules_`에서 원본 검증기 판정을 유지하고, `checkSetcAdditionalRules_`의 두 앱 전용 검토 유형을 `checkSetcLocalRules`에서 합친다. 원본 Python 규칙·사본·기준 사례에는 추가 규칙을 섞지 않는다.
- 문자 분류 데이터: Python Unicode 15.0.0. JavaScript 엔진의 다른 Unicode 버전 때문에 판정이 달라지지 않도록 범위표를 생성했다.
- `tools/build_rule_data.py`: 원본 사본에서 명칭·정규식·예외·Unicode 범위표를 생성해 전체 `.gs`의 생성 데이터 구간에 반영한다.
- `tests/build_reference_cases.py`: 합성 문장을 Python 원본으로 실행해 예상 규칙 ID·사유·검토수준을 고정한다.
- `tests/run.cjs`: Node.js에서 전체 `.gs`를 불러와 원본 결과 대조와 시트 모의 시험을 실행한다.

평상시 자동 검증은 Node.js만으로 실행할 수 있다.

```text
node tests/run.cjs
```

원본 데이터나 기준 사례를 의도적으로 재생성할 때는 Python 3.12 / Unicode 15.0.0 환경에서 다음을 실행한다. 기존 원본 해시와 판정 변경을 함께 검토해야 한다.

```text
python tools/build_rule_data.py
python tests/build_reference_cases.py
node tests/run.cjs
```

## 확인한 결과

- 합성 입력 1,238건에서 Python 원본과 JavaScript의 원본 규칙 부분의 검출 ID·오류 사유·검토수준이 순서까지 일치했다. 통합 결과에서도 이 부분이 그대로 보존되는지 확인했다. 추가 규칙과 공백 정리 시험을 포함한 자동 시험 25개 그룹이 통과했다.
- 추가 규칙에서 자모 1개/2개 경계, 자음·모음 혼합, 정상 한글·NFD 음절 제외, 한 글자 어절 2개/3개 경계, 정상 예시도 REVIEW로 검출하는 동작, 긴 연속 구간 묶음, 부분 단어·문장부호·줄바꿈 경계, 이모지 뒤 위치를 확인했다.
- 시트 모의 시험에서 두 추가 사유의 정확한 I열 문구, G열 해당 구간만 빨간색 표시, 원문 및 H열 수식 보존, 수정 후 표시·사유 해제, 기존 세특의 일괄 재검증을 확인했다.
- 공백 정리의 순수 함수 시험에서 두 칸 이상·여러 구간·앞뒤 공백·공백만 있는 입력, LF·CRLF·CR 보존, 탭·NBSP·전각 공백 보존, 이모지 뒤 위치, 재실행 결과가 같은 성질을 확인했다.
- 시트 모의 시험에서 입력·일괄 재검증 후 정리된 G열, H열 수식 보존 및 바이트 수 재계산, 이전 연속 공백 사유 제거, 남는 I열 사유·빨간 구간의 이동을 확인했다. 같은 글자 서식 구간 안의 서로 다른 링크와 굵기·기울임·글꼴도 새 위치에 보존했다. 처리 중 새 입력이 들어오면 예전 공백 정리 결과를 덮어쓰지 않는지도 확인했다.
- 사용자 보고 문장 `아버지가     법관이다.`를 별도 재현 사례로 고정했다. 공백 정리 코드가 빠진 상태에서 실패함을 확인한 뒤 해당 처리를 복구했다. 통합·기수별 명단 모두 편집 및 전체 재검증에서 `아버지가 법관이다.`·26바이트·`법관이다: 어미 오류`로 갱신되며 `법관이다`만 빨간색으로 표시되는지 확인했다.
- 같은 표현 반복, 허용 문맥과 문제 문맥의 공존, 이모지·확장 한자 뒤 UTF-16 표시 위치, 숨은 문자 설명을 확인했다.
- 기존 기준 커밋 `af58fe2`와 비교해 `onOpen`과 이수자 명단 생성 함수 2개 이외의 기존 함수 본문이 줄바꿈 정규화 후 동일함을 확인했다.
- 시트 모의 시험에서 선택 기수/전체 기수별/전체 통합, 1일·2일 이수 판정, 대기 표기 정리, 복수 이수 행 보존, 기존 명단 유지, G/I 표시·해제, H 수식 보존, I열 충돌, 수식처럼 시작하는 사유의 텍스트 출력, 오래된 편집 결과 방지, 대량 입력과 이어가기, 메뉴 보존을 확인했다.
- 순수 규칙 검사 성능을 로컬 Node.js에서 한 번 측정했다. 하이픈 50,000자 약 50ms, Google 반복 49,000자 약 196ms, 허용 예외 문맥 36,000자 약 46ms였다. 이는 실제 Google 시트 API를 포함한 처리 시간이 아니다.

## 검증 범위의 제한

원본 규칙 대조는 공백 정리 전 문자열을 받는 순수 함수로 유지한다. 실제 시트 처리에서는 일반 스페이스를 먼저 정리하고 같은 규칙을 실행한다. 따라서 시트에 출력되는 사유는 정리된 본문 기준이며, 제거된 연속 스페이스의 사유는 남지 않는다.

실제 Google Apps Script 실행·스프레드시트 화면의 글자 색·공동 편집·시트 권한·PDF 출력은 이 환경에서 실행하지 않았다. 자동 시험의 Sheets 모의 구현은 실제 서비스의 모든 동작을 대체하지 않는다. [적용 안내](APPLY.md)의 테스트 사본 확인 절차를 거쳐야 한다.

규칙 판정은 원본과 대조했으며, 표시용 위치는 추가로 수집했다. 원본이 한 단어의 첫 문맥만 보고하는 경우에도 같은 규칙에 해당하는 반복 위치를 함께 표시한다. I열에서는 같은 사유와 표현을 묶고, 표현이 매우 많으면 대표 표현과 생략 개수를 안내한다. 원문 검출 표시는 유지한다.

기본 편집 트리거의 이벤트 누락 가능성, 사용자 편집과 스크립트 쓰기 사이의 작은 시간차는 실제 서비스의 제약이다. 입력값을 쓰기 직전에 다시 확인하고, 전체 재검증 메뉴로 최신 내용의 결과를 확인할 수 있게 했다.
